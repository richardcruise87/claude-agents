### Step 1: Fetch and Analyze Each Job's Logs

For each job listed above, fetch its logs to determine why it failed.

**How to fetch logs:**

The `Log URL` for each job is the base URL of the log artifact storage directory. Append filenames to get specific files. Try these in order:

```bash
# Fetch end of main job output (most useful - failures appear here):
curl -sL "{log_url}job-output.txt" 2>/dev/null | tail -500

# If gzipped:
curl -sL "{log_url}job-output.txt.gz" 2>/dev/null | zcat 2>/dev/null | tail -500

# Search for test failures specifically:
curl -sL "{log_url}job-output.txt" 2>/dev/null | grep -nE "^(FAIL|ERROR|Traceback|AssertionError|test.*FAIL)" | tail -50

# For tempest/scenario tests, look for specific test failures:
curl -sL "{log_url}logs/testr_results.html.gz" 2>/dev/null | zcat 2>/dev/null | grep -iE "(FAIL|ERROR)" | head -30

# For unit tests (tox):
curl -sL "{log_url}job-output.txt" 2>/dev/null | grep -nE "(FAILED|ERROR|failures=|errors=)" | tail -30
```

Replace `{log_url}` with each job's actual Log URL from the details above. If curl returns empty or fails, try WebFetch with the same URL.

**What to look for in logs:**

1. **Test failures** — Lines starting with FAIL, ERROR, or containing "AssertionError", "test.*failed", specific test names
2. **Timeout** — "timed out", "Connection timed out", "No output received for", "deadline exceeded"
3. **Network/package issues** — "Could not fetch", "pip install failed", "mirror", "DNS resolution", "Connection refused during package download"
4. **Resource issues** — "No space left on device", "out of memory", "OOM", "Killed"
5. **Node/infra issues** — "lost connection to worker", "node was lost", "post-failure", "executor"
6. **Import/dependency errors** — "ImportError", "ModuleNotFoundError", version conflicts
7. **Build setup failures** — Failures in devstack setup before tests even run

### Step 2: Classify Each Failure

Assign exactly ONE category to each job:

**CODE_ISSUE** — The failure is caused by a bug or problem directly introduced by this patchset.
- The test assertion fails on code written in this change
- Import errors from modules this change touches
- Syntax errors or runtime errors in changed files
- Logic errors where output doesn't match expectations due to this change

**ENVIRONMENTAL** — Infrastructure or intermittent issue; re-running will likely succeed.
- Network timeouts while downloading packages (pip, apt, dnf, yum)
- Package mirror unavailability or slow mirrors
- Cloud resource exhaustion (no nodes available, quota exceeded)
- Timeouts in test environment setup (before tests run)
- Known intermittently failing ("flaky") tests
- Any failure with "mirror", "Connection timed out", "pip install" in the setup phase

**UNRELATED** — Pre-existing failure that exists independently of this change.
- Test fails in a module this change does not touch
- Gate failure caused by an unrelated merged change
- Failure reproducible on unmodified main/master branch

**INFRA_FAILURE** — Zuul/CI infrastructure failure; no code change can fix this.
- "lost connection to worker"
- "post-failure" without meaningful error
- Node pool exhaustion at the infrastructure level
- Zuul executor issues

## Critical Rules

1. **Always fetch real logs** — Never guess based on job names alone. Fetch logs and quote evidence.
2. **Require log evidence** — The "Key Log Evidence" section must contain actual lines from the log.
3. **Be conservative with CODE_ISSUE** — Only assign if you can clearly connect the failure to code in this specific patchset.
4. **ENVIRONMENTAL is very common** — Network timeouts, package download failures, and mirror issues are extremely common in OpenStack CI and should be categorized as ENVIRONMENTAL.
5. **Non-voting jobs still matter** — Analyze them fully, but note in the recommendation that they don't block the merge.
6. **Write the file** — Use the Write tool to save the report to {output_file}. The report must be written to disk.
7. **Complete all jobs** — Analyze every failing job listed, even if their logs are hard to fetch.
