### Step 1: Read the Triage Report

### Step 2: Read the Reproduction Report (if available)

If the reproduction report exists, read it and note:

- Number of attempts required
- The final working reproduction script (if any)

### Step 3: Examine the Source Code

Navigate to {repo_path} and read the relevant source files identified in the
triage root cause section. Specifically:
- Read the exact files and line numbers mentioned in the triage
- Read any test files that cover the affected code
- Run `git log --oneline -10 -- <affected_file>` to see recent history
- Run `git blame -L <start>,<end> <affected_file>` to understand when the bug
  was introduced

### Step 4: Generate the Patch

Write a minimal, correct patch that addresses the root cause.

Requirements for the patch:
- Targeted: change only what is necessary to fix the bug
- Tested: if unit tests exist for the affected code, add or update a test
- Clean: follow the surrounding code style, PEP 8, no trailing whitespace
- Safe: do not break existing tests (check with `grep -r "def test_" tests/ | grep <component>`)

Use `git diff` to capture the patch:
```bash
cd {repo_path}
git diff
```

Copy the full diff output — you will embed it in the proposal document.

### Step 5: Assess the Risk

Evaluate the patch against four risk dimensions:

**Scope Risk** (LOW / MEDIUM / HIGH):
- LOW: 1-2 files, < 20 lines, peripheral/utility code
- MEDIUM: 3-5 files, 20-50 lines, or touches a core path
- HIGH: > 5 files, > 50 lines, API surface, or multiple subsystems

**Confidence Risk** (LOW / MEDIUM / HIGH):
- LOW: bug was REPRODUCED, root cause is unambiguous, fix is obvious
- MEDIUM: reproduction uncertain or root cause has some ambiguity
- HIGH: NOT_REPRODUCED, root cause is inferred, or fix is speculative

**Test Coverage** (describe what exists and what the fix adds):
- Check: `grep -r "def test_" tests/ | grep <component>`
- Note whether the fix adds a new test or relies on existing coverage

**Domain Risk** (NONE / LOW / HIGH):
- NONE: no special concerns
- LOW: touches common utilities, logging, or config parsing
- HIGH: security (TLS, auth, Barbican), DB migrations, amphora protocol,
        REST API response schema changes

**Overall Risk Rating**: choose the highest of the four dimension ratings.
